# 架构和数据流

## 为什么采用外部辅助程序

需求是跨会话提醒，不依靠某一轮提示词中的“请通知我”。因此用用户级 Hook 发送机械事件，再由独立桌面程序显示。未修改官方扩展，也未将某个会话 ID 写死到监听器中。

完成事件另有 JSONL 读取通路。它对 Hook 尚未加载的当前窗口有帮助，但会话格式可能变化，不能作为稳定官方协议来宣传。

## 文件职责

| 文件 | 责任 |
| --- | --- |
| `alerts.py` | Hook 输入过滤、队列、记录读取、单实例后台、Tkinter 显示、状态与暂停 |
| `hook_config.py` | 无副作用的 Hook 合并与移除，保留其他处理器 |
| `manage.py` | 文件复制、安装清单、备份、配置检查和停用 |
| `install.ps1` | Python 检测、安装入口、用户快捷方式、后台启动 |
| `uninstall.ps1` | 通过已安装清单停用，并清理本工具的快捷方式 |

## 事件与授权

`Stop`、`PermissionRequest`、匹配提问工具的 `PreToolUse` 读取 stdin JSON。脚本只把通知元数据写入队列，stdout 返回 `{}`；不会输出 allow/deny/block，也不会把内容作为新的指令加入模型上下文。

配置在用户选定的 `CODEX_HOME/hooks.json`。安装器不修改 `notify`、`config.toml`、审批策略或 Hook 信任库。若明确配置 `features.hooks=false` 或 `allow_managed_hooks_only=true`，安装停止，让用户自行决定环境设置。管理员策略可能通过其他位置生效，本工具不会自动发现或绕过所有策略。

## 运行数据

| 文件 | 内容和生命周期 |
| --- | --- |
| `settings.json` | 选定的 Codex 数据目录 |
| `manifest.json` | 安装目录、Python 路径、Hook 路径、快捷方式等安装元数据 |
| `queue/*.json` | 一条提醒；先原子写入，显示后仍保留，用户确认后删除 |
| `queue/*.invalid` | 无法解析的队列条目，保留用于排错 |
| `history.jsonl` | 已显示过的提醒元数据；约 2 MiB 轮换，保留当前和三份旧文件 |
| `status.json` | 后台心跳、监听文件数、读取错误计数、窗口状态 |
| `errors.log` | 异常类型和时间，不写异常消息或模型正文 |
| `backups/*-hooks.json` | 安装/停用前的原 Hook 配置备份，可能包含用户私有路径与命令 |
| `paused` / `disabled` | 临时暂停 / 停用标记，防止已缓存 Hook 再次拉起进程 |

原始提示词、回答和工具输入不会进入上述提醒记录；审批去重可能使用工具输入的哈希，原文不写入磁盘队列。会话文件本身属于 Codex 的记录，本工具只读。

## 恢复和已知局限

- 用 Windows 命名互斥量避免同一安装目录启动两个实例；不同安装目录被视为不同实例。
- 未读文件在重启后再次显示，可能在历史文件出现第二次“显示记录”；历史不是唯一性审计日志。
- 同一次运行内按事件标识去重；只有无 ID 的格式时会回退到较粗的会话/轮次标识。
- 已确认提醒的去重状态不跨重启保存；边界时序下可能再次提醒。
- 没有后台服务看门狗。窗口循环或进程失败后，用 `--status` 检查，再通过桌面入口重启。
- 当前逐个 stat 所有已发现的会话文件，适合个人使用。数万文件时需要性能测试；尚未实现操作系统文件监视器。
- 超过 8 MiB 的单条记录会被跳过，避免图片等大型正文导致缓冲区无限增长；后续完整小记录仍可继续解析。
- 置顶窗口可能干扰全屏应用，暂时没有勿扰时间或最短运行时长过滤。
- 配置写入会先检查是否变化，但这不是与第三方编辑器共享的文件锁；安装期间应避免同时编辑 hooks.json。

## 后续方向

先完成真实多对话验收、更多机器兼容性和长期运行观察，再考虑原生 Windows Toast、托盘、事件分类、签名 EXE 和更稳定的事件接口。当前不承诺这些功能已实现。
